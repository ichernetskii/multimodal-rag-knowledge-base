# Управление API-ключами — 16 октября 2026

> Исторический отчёт: описывает проверенный на тот момент код. Актуальные инструкции — в [документации](../README.md); новый прототип — в [спецификации админки](../ADMIN-UX.md).

## Результат

В админке владельца «AI-подключения и ключи» реализован общий реестр: добавление, изменение названия, замена значения, включение/отключение, удаление и журнал. В профиле модели выбирается сохранённый ключ соответствующего поставщика. Поддерживаются Google, Anthropic и серверы с OpenAI API. Ollama и Whisper работают без внешних ключей.

Реестр общий для установки; каталоги моделей относятся к компаниям. Администраторы компаний, редакторы и пользователи не могут читать или менять реестр. Проверки выполняются сервером на каждом вызове, а не только скрывают меню.

## Хранение и применение

- PostgreSQL хранит AES-256-GCM ciphertext, случайный nonce и authentication tag. HKDF отделяет ключ шифрования от назначения подписей резервных копий; alias/provider защищены authenticated data.
- Мастер-ключ APP_ENCRYPTION_KEY остаётся в приватной конфигурации сервера. Отсутствующий, неверный или нулевой ключ отклоняется во всех окружениях. Старого механизма AI_SECRETS и автоматического переноса из окружения нет.
- HTTP/CLI возвращают только метаданные. Даже владелец не может получить сохранённое значение, ciphertext, nonce или tag. Новое значение передаётся однократно при сохранении и не попадает в аудит, Redis или задания.
- API и воркеры читают актуальный включённый ключ из БД непосредственно перед вызовом провайдера, после ожидания доступной мощности. Перезапуск, рассылка инвалидирования и кеш расшифрованных значений не нужны.
- Отключение блокирует новые вызовы; уже отправленные запросы могут завершиться. Кешированные ответы могут выдаваться без обращения к провайдеру. Удаление из приложения не отзывает ключ у поставщика.
- Удаление блокируется ссылками во всех компаниях, включая выключенные профили. Запись профиля и удаление ключа используют общий transaction lock. Глобальные revisions защищают и от устаревших форм после удаления/повторного создания alias.
- Журнал ключей отдельный и доступен только владельцу. Копии компаний не содержат реестр/его аудит; восстановление компании не меняет актуальные ключи. Полный PostgreSQL snapshot содержит зашифрованный реестр и требует отдельно сохранённого мастер-ключа.
- Production требует HTTPS для подключения с API-ключом. HTTP API сохраняет существующие same-origin/CSRF-проверки и Cache-Control: no-store.

## Проверки

- `yarn validate`: документация и 81 action, текущие контракты, TypeScript, ESLint, форматирование, 23 серверных и 27 клиентских тестов, production-сборки. Криптографические unit-тесты отдельно проверяют tamper/wrong-key rejection и запрет некорректного мастер-ключа. Интеграционный тест выполняется отдельно.
- [Интеграционный протокол](credential-vault-integration-2026-10-16.tap): шифрование, живая замена и генерация через отдельный заранее запущенный потребитель, отключение без исходящего запроса, безопасные ошибки провайдера, все клиентские роли, анонимный доступ/CSRF, конкурентные изменения, ссылки другой компании, защита после повторного создания alias, изоляция company backup/restore.
- [Docker-проверка](credential-vault-docker-2026-10-16.json): синтетический ключ заменён через API; отдельный процесс в контейнере worker-answers расшифровал текущее значение. Время запуска API и воркера не изменилось. Все клиентские роли получили 403 на операции реестра.
- [CLI](credential-vault-cli-2026-10-16.json): login, метаданные, сохранение без замены значения, журнал; приватная временная сессия удалена.
- Браузер: реестр владельца, пустое поле замены, сохранение названия без секрета, закрытие формы после сохранения, журнал, фильтрация ключей в редакторе моделей, отказ клиентскому администратору. Для формы ключа отключено обычное автозаполнение и используется new-password, чтобы не подставлять пароль входа.
- Проверки использовали только синтетические значения и локальный HTTP-стенд. Настоящие ключи и платные облачные вызовы не использовались.

Первый расширенный интеграционный прогон достиг таймаута резервной копии. Два последующих полных прогона прошли; причина первого таймаута не установлена. Отдельные проверки реестра и Docker/CLI завершились успешно.

Под новую несовместимую схему пересозданы локальные PostgreSQL/S3 окружения разработки и Docker-приложения согласно AGENTS.md. Веса Ollama сохранены; Qwen, EmbeddingGemma и Whisper доступны. Временные компании, аккаунты и синтетические ключи удалены; метаданные аудита операций оставлены. Реестр готов для добавления владельцем настоящих ключей.
