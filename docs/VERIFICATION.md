# Проверка и границы результата

Автоматические тесты, настоящие модели, ручная проверка браузера и установка системных служб дают разную степень подтверждения. Протоколы в [verification/](verification/) сохраняют дату конкретного прогона. Перенос или редактирование документации не обновляет дату проведённого эксперимента.

## Быстрая проверка текущего кода

Из корня с Node из [.nvmrc](../.nvmrc):

```sh
node .yarn/releases/yarn-4.18.1.cjs install --immutable
yarn validate
```

Модели, Ollama, системный OCR и рабочая установка не нужны для обычного validate. Набор использует изолированные временные каталоги и тестовые адаптеры там, где проверяется политика приложения. Он включает:

- локальные ссылки/разделы Markdown и полноту справочников команд, env-примеров и API actions;
- совпадение генерируемых контрактов, TypeScript, ESLint и Prettier;
- границы workspace, runtime-зависимости и циклы импортов;
- сессии, ACL, кеши, версии, ветки диалога, удаление и отмену во время генерации;
- SQLite backup/restore, конфликты writer, несовместимую схему, ошибки диска и сроки хранения;
- HTTP, CSRF, SSE через тестовый потоковый proxy, несколько клиентов и медленного читателя;
- безопасный Markdown, клиентский пул SSE, отдельный gateway и обе production-сборки.

Последние сохранённые числа и дата — в [checks.json](verification/checks.json). Это протокол выполненной проверки, а не автоматически обновляемый отчёт каждого запуска validate. Линтер/сборка не заменяют просмотр интерфейса или контроль реальной модели.

## Сквозная проверка с настоящими моделями

Подготовьте embedding (`yarn cli setup`), локальную Ollama с выбранной моделью и PDF/OCR (`yarn prepare:pdf`). Затем:

```sh
yarn test:product:live
```

[Сценарий](../server/scripts/test-product-live.ts) создаёт временный сервер на свободном loopback-порту. Он не использует рабочую БД и не создаёт в ней примеры. Входы — [фиксированные PDF](../server/tests/fixtures/pdf/README.md): текстовый, скан, смешанный и таблица. Генерация PDF и reportlab для запуска не требуются.

Проверяется цепочка:

1. Чистая установка, администратор, пользователь и права на базы.
2. Загрузка четырёх PDF, избирательный OCR, проверка страниц и связи заголовков таблицы со значениями.
3. Индексация, точный поиск, настоящий потоковый ответ и разрешимые цитаты.
4. Оригинальные байты PDF, конкретная страница, Range и сохранённая ссылка после переиндексации.
5. Новая версия документа и новый ответ, явное противоречие источников и контрольный набор.
6. Отзыв прав, недоступность кешированного поиска и SSE.
7. Согласованная копия, восстановление в отдельный каталог, старт восстановленного HTTP-сервера, открытие старого источника, диагностика и поиск.

Только успешный запуск записывает [live.json](verification/live.json); временная установка удаляется в finally. Ошибка возвращает ненулевой exit code и не заменяет предыдущий успешный протокол. Перед интерпретацией файла проверьте его дату.

Сохранённый прогон 15 октября 2026, 05:21–05:28 UTC: EmbeddingGemma, qwen3.5:4b и Apple Vision. Восстановлены 2 пользователя, 2 базы, 4 документа, 5 версий, 1 диалог, 3 сообщения, 12 завершённых заданий и 2 результата контроля; SQLite-этап восстановления занял 46 мс. Это малый набор: время подготовки моделей, OCR и запуска HTTP не входит в эти 46 мс.

## Ручная приёмка интерфейса и deployment

Для браузера используйте отдельный каталог данных и порты, чтобы не менять реальные учётные записи. Проверьте первый запуск, загрузку/предпросмотр, поток, источники, версии вопроса, экспорт, черновик после reload, отзыв доступа, все семь разделов админки, ошибки форм, мобильную ширину и клавиатуру. Повторяйте после изменений соответствующих сценариев.

## Производительность

```sh
yarn benchmark
# Другой путь отчёта, каталог создаётся автоматически:
yarn benchmark /tmp/local-rag-benchmark/results.json
```

Benchmark создаёт временный детерминированный SQLite-корпус и удаляет его после проверки; отчёт остаётся по указанному пути, по умолчанию `.cache/benchmark.json` от корня. `BENCH_CHUNKS` меняет число фрагментов; это инструмент измерений, не параметр runtime сервера. По умолчанию: 3000 фрагментов, 128 измерений вектора, 3000 заданий, 120 диалогов/1440 сообщений, 60 документов. Inference, OCR и HTTP исключены; вместо embedding используется детерминированный тестовый адаптер.

[performance.json](verification/performance.json) сохраняет историческое сравнение на одном наборе 15 октября 2026, включая сырые выборки. Медиана поиска без кеша: 739,33 → 59,97 мс; из кеша: 299,63 → 0,36 мс. RSS benchmark-процесса: примерно 351 → 121 МиБ. Это не память полного ONNX/Ollama runtime. Отдельный тест чтения диапазонов 64 КиБ оригинала 16 МиБ также исключает HTTP. Фоновая нагрузка машины не контролируется; эти цифры не SLA и не обещание текущей задержки. Для сравнения нового кода повторяйте одинаковый набор и сохраняйте собственный отчёт.

## Ограничения

- Один SQLite writer; несколько API-процессов с общим каталогом не поддерживаются.
- Семантический поиск — перебор разрешённых векторов, без ANN. Большой корпус требует собственного замера.
- Четыре небольших PDF не представляют все варианты сложной вёрстки, шифрования и OCR. Предпросмотр текста остаётся обязательным.
- Проверка фактов ищет ожидаемые строки и источники; она не является экспертной оценкой произвольного ответа. Качество зависит от модели, промпта и документов.
- RLIMIT_AS OCR применяется на Linux; для общего потолка памяти macOS нужны средства ОС. Автоматический proxy-тест не заменяет приёмку фактического nginx/TLS.
- Offline-работа требует заранее подготовленных assets и пакетов для целевой ОС/архитектуры. Службы, сертификаты и модели не восстанавливаются из пользовательского SQLite backup.
