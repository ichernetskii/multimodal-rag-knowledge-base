# Установка и эксплуатация

## Подготовка и автономная работа

Используйте Node 24.19.0, закреплённый Yarn и поддерживаемую архитектуру нативного ONNX runtime. Нативный запуск PDF/OCR проверяется на macOS; Docker предназначен для Linux с Tesseract. Windows запускайте через Linux/WSL2. Python 3.10+ устанавливается отдельно; зависимости PDF из `server/requirements-pdf.txt` устанавливаются в `server/.venv`, системный Python не изменяется.

Первый запуск описан в [README.ru.md](../README.ru.md). Используйте закреплённый Yarn; глобальная команда не обязательна. `yarn cli setup` подготавливает только embedding, не учётную запись. Из корня: `node .yarn/releases/yarn-4.18.1.cjs install --immutable`, `yarn configure`, `yarn cli setup`, `yarn prepare:pdf`, `yarn build`. Отдельно запустите Ollama и подготовьте выбранную модель, например `ollama pull qwen3.5:4b`. Только подготовка зависимостей и весов требует интернета. Модель embedding закреплена профилем, ревизией и SHA-256; обычный сервер не скачивает отсутствующие файлы.

Для автономной установки сохраните код, lockfile, Yarn и пакетный кеш; установите зависимости на целевой ОС/архитектуре. Python wheels готовятся `yarn prepare:pdf --download`, устанавливаются `yarn prepare:pdf --offline`; виртуальное окружение лучше создавать на целевой машине, поскольку его launchers содержат пути. На macOS подготовка собирает Apple Vision OCR с установленным Swift SDK; на Linux установите Tesseract и языки, например eng/rus. Перенесите проверенный каталог embedding и отдельно модели Ollama. Веса моделей не входят в пользовательскую резервную копию.

## Запуск и первоначальный мастер

`yarn start` запускает два процесса: compiled API на 127.0.0.1:3210 и клиентский gateway на **http://127.0.0.1:8080/**. `yarn dev` открывает клиент на 5173. API самостоятельно HTML не отдаёт. Клиент можно обслуживать отдельным nginx; сервер запускается независимо командой `yarn start:server`.

Мастер создаёт администратора, выбирает каталог и основные лимиты, показывает модели/оборудование, принимает первую базу и ведёт к контрольному вопросу. Тестовые пользователи и документы автоматически не создаются. Первичная настройка разрешена с локального подключения; в контейнере используйте локальную CLI `api setup.create`, как описано ниже в разделе Docker Compose.

Настройки процесса находятся в `server/.env`, клиента — в `client/.env`. Полный справочник, приоритеты и сохранение runtime — в [CONFIGURATION.md](CONFIGURATION.md). Относительные серверные пути разрешаются от `server/`. По умолчанию данные — `server/data`, модели — `server/.cache/models`, копии — `server/data/backups`. В production используйте абсолютные каталоги вне установки кода, например `/var/lib/local-rag`, `/var/cache/local-rag/models` и `/mnt/local-rag-backups`. Явный `RAG_BACKUP_DIR` задаёт место копий текущей установки. Если мастер выбирает другой каталог данных, `data-location.json` в исходном каталоге сохраняет указатель для сервера и CLI.

`.writer-lock/pid` исключает второй writer SQLite. После аварии сначала проверьте, что указанный процесс остановлен; только затем удаляйте оставшуюся блокировку. Не запускайте две серверные реплики для одного каталога. Обычная CLI обращается к HTTP работающего сервера, а не пишет в его БД.

Если Ollama недоступна, библиотека, оригиналы, история и администрирование продолжают работать. Новое задание генерации получает контролируемую техническую ошибку. Браузер использует локальные assets без CDN, внешних шрифтов и аналитики.

## Docker Compose

Настройте [compose.env](../compose.env.example), затем из корня:

```sh
docker compose --env-file compose.env build
docker compose --env-file compose.env run --rm server node server/dist/interfaces/cli/main.js setup
docker compose --env-file compose.env up -d
```

Первый запуск build и setup требует сети для образов, пакетов и embedding. Модель Ollama подготовьте отдельно на доступном контейнеру endpoint. Серверный образ включает Python, PDF runtime, Tesseract eng/rus. Для автономного запуска заранее сохраните образы и заполненный model volume; повторная сборка offline не требуется.

Порт клиента по умолчанию опубликован на 127.0.0.1:8080, API наружу не публикуется. Откройте **http://localhost:8080/**: origin должен совпадать с RAG_PUBLIC_ORIGIN. Если меняете hostname, HTTPS или порт, обновите это значение. Внутри Compose клиентский nginx проксирует API по имени сервиса и повторно разрешает Docker DNS после пересоздания API.

Вход первого администратора через nginx считается внешним подключением. Создайте его локальной CLI в работающем контейнере; `/secure/setup.json` на host содержит `{"login":"admin","password":"<12+ символов>"}`:

```sh
docker compose --env-file compose.env exec -T server node server/dist/interfaces/cli/main.js api setup.create < /secure/setup.json
docker compose --env-file compose.env exec -T server node server/dist/interfaces/cli/main.js login admin < /secure/password.txt
docker compose --env-file compose.env exec server node server/dist/interfaces/cli/main.js diagnose
```

После этого войдите в браузере, создайте базу и загрузите документ. Сохранённый CLI-токен принадлежит контейнерной установке. Для внешнего HTTPS нужен TLS ingress и точный публичный origin; API должен оставаться в закрытой сети.

У API и клиента отдельные [Dockerfile сервера](../server/deploy/Dockerfile) и [клиента](../client/deploy/Dockerfile), health, CPU/RAM/логи и read-only runtime. Volumes данных/весов/копий перечислены в [compose.yaml](../compose.yaml). Host-каталоги подготовьте для UID 1000. Для защиты от отказа основного диска замените RAG_BACKUPS_VOLUME на абсолютный каталог другого носителя. Папки синхронизации подключайте явными read-only mounts и указывайте путь внутри контейнера. Полный список переменных — в [конфигурации](CONFIGURATION.md#docker-compose).

## Службы и прокси

Шаблоны:

- [API systemd](../server/deploy/local-rag.service), [API launchd](../server/deploy/com.local-rag.plist);
- [клиентский systemd gateway](../client/deploy/local-rag-client.service);
- [nginx для Docker](../client/deploy/nginx.conf), [nginx с TLS для отдельной установки](../client/deploy/nginx-tls.conf).

Укажите действительные пути Node, установки, пользователя и сертификатов. Создайте данные, кеш и каталог копий с правами пользователя службы. Подготовьте модели от того же владельца. В systemd-примере `ReadWritePaths` должны соответствовать вашим `RAG_DATA_DIR`, `RAG_BACKUP_DIR` и `EMBEDDING_CACHE`; окружение API читается через `EnvironmentFile`. Клиентская служба независимо читает свой env и может запускаться раньше API. Для nginx отдельный Node gateway не требуется.

За HTTPS задайте `RAG_PUBLIC_ORIGIN` равным точному origin браузера и `TRUST_PROXY=1`; API оставьте в закрытой сети/на loopback. Cookie получает Secure для HTTPS, записи проверяют Origin. SSE использует HTTP/1.1, heartbeat, отключённые buffering/cache и read timeout выше heartbeat. Нативный gateway и nginx проксируют потоки с backpressure; отключение клиента закрывает upstream. В Docker клиент повторно разрешает DNS сервера после его пересоздания.

Health разделён: `/health/live` — процесс; `/health/ready` — готовность приёма заданий; авторизованный `/health/dependencies` — модели. У клиента есть самостоятельный `/_client/health`. Не используйте готовность генерации для отключения чтения документов. Клиентский контейнер может оставаться доступным при недоступном API.

## Доступ и CLI

Права проверяются на сервере при поиске, выдаче кеша, чтении истории, источников, заданий и SSE. Назначения read/edit задаются пользователям и группам; личные вложения принадлежат диалогу. Изменения прав немедленно учитываются действующими сессиями. Роли и пользовательские действия — в [USAGE.md](USAGE.md).

Полный справочник команд, stdin/JSON, exit codes и локальное recovery без email — в [CLI.md](CLI.md). Обычные CLI-команды используют работающий HTTP API. Локальный recovery.key даёт административный доступ: ограничивайте владельца и права файла. Ключ и CLI-токен не передавайте в технические журналы и не копируйте в браузерную конфигурацию.

## Очереди, ресурсы и очистка

В админке видны CPU/RAM, свободный диск, очереди по типам и их возраст, работающие задания, измеренное время ответа и доля ошибок за 24 часа, объём данных/кешей и состояние копий. Это измерения, а не ETA/проценты выполнения. Поиск, генерация, отсутствие данных, уточнение, отмена, прерывание и техническая ошибка отображаются отдельно.

Планировщик выделяет по одному активному заданию для ответа, индексации и качества. Query embedding использует отдельный ONNX runner с настроенным числом потоков; индексация — другой runner с одним потоком. OCR запускается только при отсутствии пригодного текстового слоя. На Linux ограничиваются память процесса и CPU; на всех поддерживаемых системах действуют таймаут страницы, пределы страниц/текста/фрагментов и отмена всей группы дочерних процессов. Временные изображения находятся внутри каталога задания и удаляются также при отмене.

Админка позволяет приостановить индексацию, запуск очередей и приём новых заданий. Пауза очередей останавливает запуск новых answer/document/evaluation, но не отключает расписания копий и синхронизации; интервалы этих расписаний меняются отдельно. Уже начатая генерация продолжается, пауза индексации проверяется между пакетами. Приём ограничен размером файлов, количеством документов/заданий и свободным местом. Одновременно сервер принимает не больше двух upload-запросов. Оригиналы хранятся блоками по 64 КиБ в SQLite; HTTP Range не материализует файл целиком. Скачивания/экспорты ограничены 16 активными операциями, backpressure-таймаутом и временем операции; обслуживание отменяет их перед заменой БД.

SQL-кеш ограничен 1000 записями и 64 МиБ UTF-8; векторный LRU — 32 МиБ; кеш embedding вопроса — 128 запросами. У клиента максимум четыре SSE, при массовой загрузке документы занимают не больше трёх. У сервера — восемь на пользователя; события/размер snapshot/буфер медленного клиента ограничены. Token-записи ответа объединяются с интервалом 100 мс, отмена сохраняет последний разрешённый фрагмент.

`historyDays`, `jobDays`, `tempHours`, `logDays` и `backupDays` задаются в админке. Очистка запускается раз в час или через `yarn cli cleanup`; данные незавершённых заданий сохраняются. Архивирование и исключение из поиска сохраняют оригинал и историю; окончательное удаление очищает версии, блоки оригинала, индекс/FTS, кеши и производные ссылки/ответы. Технические логи содержат коды и диагностические UUID, без полного текста документов и диалогов. ENOSPC/SQLITE_FULL возвращают `DISK_FULL`; ошибка записи журнала не создаёт рекурсивный сбой. Для stdout/stderr systemd/launchd/nginx задайте внешнюю ротацию; Compose уже ограничивает логи.

## Резервное копирование и восстановление

Админка и `yarn cli backup` используют SQLite online backup API. В одной согласованной копии находятся оригиналы, страницы/версии, векторы/FTS, пользователи, конфигурация обработки, история, результаты и задания. Открытый файл БД произвольно не копируется. Перед публикацией копии проверяются SHA-256, SQLite integrity, текущая схема, связи, последовательность и хеши блоков оригиналов, валидность векторов. Рядом сохраняется `<имя-копии>.sqlite.sha256`; незавершённый файл `.partial` удаляется при ошибке.

Задайте `backupDir` на другом диске, `backupIntervalHours` и `backupDays`. Просроченные копии удаляются при следующем успешном создании копии, а не отдельным таймером TTL. Флаг verified в списке означает наличие sidecar `.sha256`; для повторной проверки выполните backup.verify. Сервер должен работать для выполнения локального расписания. Список — `yarn cli backups`; проверка — `yarn cli api backup.verify` с JSON `{id}`. Named volume на том же диске не защищает от отказа диска: используйте другой носитель или резервное хранилище.

Для отдельной остановленной установки:

```sh
yarn cli restore-installation /other-disk/backup-....sqlite /new/data
```

Перенесите также `.sha256`. Восстановление проверяет копию, блокирует каталог назначения и сохраняет rollback-снимок. Online restore в админке блокирует новые действия, отменяет скачивания, дожидается запросов и останавливает активную работу перед заменой БД. Остановка службы дожидается начатого восстановления/backup. При ошибке восстанавливается rollback-снимок. Сессии отзываются; завершённые задания не ставятся в очередь, незавершённые становятся interrupted.

Физические каталоги и endpoint модели привязываются к новой машине, семантические параметры сохраняются. Подготовьте embedding и Ollama отдельно. Live-сценарий запускает восстановленную установку на отдельном HTTP-порту, повторно открывает оригинал, выполняет диагностику и поиск. Данные и измеренное время приведены в [live.json](verification/live.json); это малый контрольный набор, не обещание времени для произвольного объёма.

### Проверка переноса на отдельную установку

1. В исходной установке создайте копию и выполните backup.verify; сохраните пару `.sqlite` / `.sqlite.sha256` на другой носитель.
2. Выберите отдельный остановленный каталог назначения и восстановите его командой restore-installation. Не копируйте открытую catalog.sqlite произвольно.
3. Задайте абсолютный RAG_DATA_DIR назначения, отдельный RAG_PORT и актуальные пути/endpoint моделей. Offline restore задаёт backupDir внутри нового каталога; при необходимости переопределите его RAG_BACKUP_DIR.
4. Запустите API, войдите заново, выполните diagnose и проверьте пользователей, версии/оригиналы, выбранную ветку истории, поиск и сохранённый завершённый результат. Модели и env-файлы восстановлением не устанавливаются.
5. Запишите состав, объём и время восстановления. Завершённые задания должны оставаться завершёнными; незавершённые — interrupted. Для контрольного вопроса используйте новую генерацию явно.

Резервная копия содержит персональные документы и историю: храните её с ограниченными правами. Файл recovery.key и env-файлы не входят в SQLite-копию. На новой установке ключ recovery создаётся при старте; внешние адреса/сертификаты/службы настраиваются отдельно. Старые файлы копий не вложены в новую копию.

## Обновление до первого релиза

Поддерживается ровно один контракт и одна схема: application_id `0x52414736`, user_version 1 и SHA-256 текущей структуры/контракта. Совпадения user_version недостаточно. Несовместимые данные и копии отклоняются до изменения существующей БД; миграций и адаптеров нет.

1. Создайте и проверьте копию на другом носителе. Сохраните прежнюю версию кода и зависимостей.
2. Приостановите приём и очереди, завершите/отмените активную работу; остановите обе службы.
3. Установите код, выполните immutable install, validate и обе сборки. Проверьте формат данных до запуска основной установки.
4. При смене схемы используйте пустой каталог разработки. Старые данные не преобразуются. Копия текущего формата может быть проверена восстановлением в отдельный каталог.
5. При намеренной смене embedding/чанкинга задайте `RAG_USE_SAVED_CONFIG=0`, запустите диагностику и переиндексацию документов. До переиндексации несовместимый поиск возвращает `INDEX_INCOMPATIBLE`. Смена модели ответа/промпта не меняет векторы, но требует контрольных вопросов.
6. Обновите client/dist и server/dist как одну версию контракта, запустите обе службы, выполните диагностику, контрольный вопрос и открытие источника.
7. Для отката верните прежний код и соответствующую ему копию в отдельном каталоге. Текущий сервер не преобразует формат прежней версии.

Качество проверяется по пяти отдельным признакам: нужный источник, ожидаемые факты, ссылки, отказ без данных, время. Проверка фактов сопоставляет заданные строки; она не доказывает истинность произвольного ответа. Проблемные ответы разбираются вручную с версиями источников и настройками. Feedback никогда автоматически не изменяет знания.

## Диагностика неисправностей

| Симптом / code                                        | Что проверить и сделать                                                                                       |
| ----------------------------------------------------- | ------------------------------------------------------------------------------------------------------------- |
| Клиент открыт, API недоступен / SERVER_UNAVAILABLE    | Проверить /_client/health отдельно от /health/live, порт/службу API и proxy target                            |
| /health/ready возвращает 503                          | Прочитать reason: мастер, pauseIntake, диск, очередь или maintenance; чтение библиотеки не отключать          |
| GENERATION_UNAVAILABLE / GENERATION_TIMEOUT           | Проверить Ollama, подготовленную settings.model и таймаут; документы и история остаются доступны              |
| INDEX_INCOMPATIBLE                                    | Сверить сохранённый runtime, веса и параметры embedding/чанкинга; переиндексировать актуальные версии         |
| WRITER_RUNNING                                        | Не удалять lock у работающего процесса; проверить точный PID и каталог, остановить лишнюю реплику             |
| SCHEMA_INCOMPATIBLE                                   | Версия кода и формат данных различаются; выбрать соответствующий код/копию либо новый пустой dev-каталог      |
| PDF_EXTRACTION_FAILED / OCR_UNAVAILABLE_OR_FAILED     | Проверить prepare:pdf --check, PDF_PYTHON, OCR backend/языки и лимиты; просмотреть страницы                   |
| CONTENT_LOSS / REVIEW_REQUIRED                        | Исправить исходный файл или OCR и просмотреть извлечение; acknowledge не обходит пустые страницы              |
| REVISION_CONFLICT                                     | Перечитать запись, сопоставить правку другого пользователя и отправить актуальную revision                    |
| ORIGIN_REJECTED / CSRF_REJECTED / вход не сохраняется | Сверить точный origin, HTTPS/Secure cookie, Host и RAG_PUBLIC_ORIGIN; не отключать серверную проверку         |
